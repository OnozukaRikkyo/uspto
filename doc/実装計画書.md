# 実装計画書

原則: **1 項目 = 1 タスク**。項目番号は実行順(依存関係の上流から)に付けている。各項目の見出しに担当系統・着手時期・後続を記す。

作業は資源で 3 系統に分け、常に並行させる:

- **データ取得作業**(CPU・通信回線): 項目 1・5
- **GPU 推論作業**(推論のみ。判定・埋め込み生成): 項目 2・4・12・14
- **実装・学習作業**(コード実装と GPU 学習): 項目 1.1・1.2・3・6〜11・13・15〜18 → 19・20

着手順:

- **即日起動(長時間タスク)**: 項目 1、項目 2、項目 4 の準備。時間のかかる実行を先に流し始めることを最優先とする。
- **項目 1 完了直後**: 項目 1.1・1.2 を順次実行(各 1 日程度)。項目 12 を開始するための前提条件。
- **長時間タスクの実行中に実施**: 項目 6〜11(評価系とモデル実装)、項目 15・16 の実装。評価系の凍結期限は項目 19 の学習開始前。学習開始後の仕様変更は全学習の再実行になるため、この期限のみ厳守。
- **最終**: 項目 19・20(全上流の成果物を消費)。

### 項目 1: IMPACT で不足している意匠特許の取得
**データ取得作業 / 即日着手 / 所要は要調査 1・2 の結果で確定 / 後続: 項目 1.1**

取得対象は「2007 年以降に登録された全意匠特許のうち IMPACT にない全件」のみ。既存分の取り直しは行わない。**データソースと出力形式は IMPACT と同一にする**(調査済み: IMPACT は BDSS の「TIFF 埋め込み特許付与全文データ」の tar から XML を解析して 11 フィールドの年別 CSV を作り、TIF は USDID-日付 形式のフォルダに保存している。IMPACT リポジトリの Data processing コードを流用する)。以下の 3 プログラムを実装する。

**(1) 対象列挙 `list_missing_patents.py`**
- 入力: Open Data Portal の特許一括テーブル(所在は要調査 1)、IMPACT 由来の既存マスタの特許番号一覧。
- 処理: ① 一括テーブルから意匠区分かつ登録日 2007 年 1 月 1 日以降の全特許番号を抽出。② **特許番号を IMPACT の形式(D+7 桁ゼロ埋め。例: D0908314)に変換**する(Open Data Portal 側はゼロ埋めなしが通例のため)。変換後、先頭 100 件がマスタの形式と一致することを確認する(不一致なら停止)。③ マスタとの差分を取る。
- 出力: `missing_patents.parquet`(列: 特許番号、登録日)。
- 検証(単体テスト): 差分リストとマスタの共通部分が空であること。差分リスト+マスタ = 抽出した全列挙、であること。

**(2) 全文アーカイブからの展開 `extract_grant_fulltext.py`**
- 入力: `missing_patents.parquet` と、BDSS の TIFF 埋め込み特許付与全文アーカイブ(対象年分をダウンロード)。
- 処理: tar から差分リストの意匠特許のみを取り出し、XML を解析して **IMPACT と同一の 11 フィールド**(title, id, claim, date, class, class_search, inv_country, no_figs, sheets, file_names, fig_desc, caption)を年別 CSV に出力する。**caption は生成せず空欄とする**(LLaVA 生成物で当方のパイプラインは使用しない)。TIF は IMPACT と同一の USDID-日付 フォルダ構成で保存する。**代表図の選定は fig_desc の視点記述(perspective view の解析)に既存規則をそのまま適用する。**
- 出力: 年別 CSV(既存 CSV と同一スキーマ)+ TIF フォルダ+ `image_manifest.parquet`(特許番号、フォルダパス、代表図ファイル名、取得日)。
- 検証: 展開できなかった特許の一覧をログに記録。**再実行時は manifest にある特許をスキップする(途中で中断しても最初からやり直しにならない)。** 展開済みアーカイブは削除する。
- 譲受人は 11 フィールドに含まれないため、Open Data Portal の譲受人テーブルから差分リスト分のみ取得して結合する。

**(3) 引用取得 `fetch_citations.py`**
- 入力: `missing_patents.parquet` と、Open Data Portal の引用テーブル。
- 処理: 差分リストの特許の審査官引用のみを抽出する(引用は全文 XML ではなくこちらから取る。office action 識別子を含むため)。
- 出力: `missing_citations.parquet`(1 行 1 引用。列: 特許番号、被引用特許番号、office action 識別子)。
- 検証: office action 識別子の欠損率をログに記録する(要調査 3 の実測を兼ねる)。

### 項目 1.1: 取得データの統合・検証

### 項目 2: 会社別名 JSON の生成
**GPU 推論(数時間)+データ取得作業 / 所要 1 日 / 即日着手 / 後続: 項目 3**

方針(3 択): **(a) Qwen がツール検索で裏付け URL を得て、かつ会社名テーブルに実在すると確認できた別名のみ記録する。(b) 確認できなければ何もしない。(c) 入力ミスや確実に知っている別名は人が同じ形式で追記する。** 中間ケースは扱わず未併合のまま残す。

**用語の定義**(項目 2・3 で一貫して使う):

- **会社名**: 正規化済み譲受人名の相異なる文字列。約 2.7 万件。
- **照会対象**: 調査対象の会社名。特許件数上位 2,000 件。
- **別名グループ**: 同じ会社を指す会社名のリスト。根拠(URL または追記理由)を必ず伴う。**先頭が代表会社名**。有効範囲はそのグループが書かれたファイルのクラス。例: `{"names": ["INTERNATIONAL BUSINESS MACHINES", "IBM"], "source": "https://www.wikidata.org/wiki/Q37156"}`
- **会社別名 JSON**: 別名グループの配列。**意匠クラスごとに 1 ファイル**とし、ファイル名にクラスを記す(`company_aliases_D14.json`)。同じ会社が複数クラスに出願していれば、該当する各クラスのファイルに同じ別名グループが書かれる。プログラムの自動書き込みと人手追記(例: `{"names": ["MICROSOFT", "MICORSOFT"], "source": "入力ミスの修正"}`)の 2 経路。規約: **同一ファイル内で**同じ会社名を 2 つ以上のグループに入れない(違反時は項目 3 が停止、ファイルを直して再実行)。
- **代表会社名**: 別名グループの先頭の会社名。どのグループにも属さない会社名は自身。会社名は同じ会社に複数あり得るが、代表会社名は同じ会社にちょうど 1 つ。
- **確定テーブル**: 項目 3 の完了後に固定する最終出力。「特許番号 → 代表会社名」の表(parquet)。下流(項目 14・15・16・17)が読む唯一のインターフェース。

実装 `build_company_aliases.py`:

- ツール: `search_web(query)`(検索 API ラッパー)、`find_company(text)`(会社名テーブルの部分一致検索・大文字小文字無視。該当する会社名を返す)。
- プロンプト(照会対象 1 件につき 1 回、温度 0)。`{company}` は Python 側で埋めるプレースホルダ:

```python
PROMPT_TEMPLATE = """Company: {company}
Task: Find former names or well-known aliases of this company using
search_web. For each candidate alias, call find_company to check whether
it exists in our table. Output ONLY the aliases that exist in the table,
as JSON: {{"names": ["{company}", "<alias1>", ...], "source": "<URL>"}}.
The URL must be a search result that supports the alias. If nothing is
confirmed, output {{"names": [], "source": ""}}.
Do not include subsidiaries or similarly-named different companies."""

# 設定例
company = "INTERNATIONAL BUSINESS MACHINES"   # 会社名テーブルの 1 行
prompt = PROMPT_TEMPLATE.format(company=company)
```

`str.format` を使うため、プロンプト本文中の JSON の波括弧は `{{ }}` とエスケープする(上のとおり)。照会対象 2,000 件のループでこの `prompt` を Qwen に渡す。

- 検証(コード側のロジック): `names` 全要素が会社名テーブルにそのままの文字列で実在し、`source` が URL であること。満たさない出力は破棄してログに記録。通過した出力について、全会社名が出願している意匠クラスを特許マスタから求め、該当する各クラスのファイルに別名グループを書き込む。共通クラスがなければ破棄してログに記録。
- 出力: 会社別名 JSON、照会対象 1 件 1 行のログ(採用/破棄/確認なし)。

### 項目 3: 併合と確定テーブル出力
**実装・学習作業 / 所要 0.5 日 / 項目 2 完了直後 / 後続: 項目 14・15・16・17**

実装 `apply_merge.py`(入力: 特許マスタと会社別名 JSON):

```
1. 全クラスの会社別名 JSON を読み、ファイルごとに検査する。
   同一ファイル内で同じ会社名が 2 つ以上のグループにある、
   根拠がない、テーブルにない文字列がある、ファイル名のクラスに
   出願していない会社名が names にある——いずれかで停止
2. 各別名グループについて、(ファイル名のクラス, 会社名) → 先頭
   の対応を辞書に登録する
3. 各特許について、(その特許のクラス, 会社名) が辞書にあれば
   対応する代表会社名を、なければ会社名そのものを
   確定テーブルに書き込む
```

出力は確定テーブル `patent_company.parquet`(列: 特許番号、会社名、代表会社名、バージョン)の 1 ファイル。ハッシュ値とバージョンを記録。根拠は会社別名 JSON が担うため別ファイルは作らない。

### 項目 6: 特許粒度の統一評価
**実装・学習作業 / 長時間タスクの実行中に実施 / 後続: 項目 7・8・9**

前提となるデータ形式: 各縮約条件(項目 7・15・16・17)は**縮約対応表** `contraction_map_{条件}.parquet`(列: 特許番号、縮約ノード ID)を出力する。縮約なしの条件は恒等写像の対応表を持つ。

実装 `expand_predictions.py`: 現行モデル(DyGFormer 型)は縮約グラフでも階層的読み出し [h_family(u) ∥ proj(x_u)] により**既に特許粒度で採点している**。本プログラムの役割は 2 つ: (a) 特許粒度のスコアをそのまま受け取る経路(現行モデル用)と、(b) **縮約ノード粒度でしか採点できないモデル**(項目 11 のハイパーグラフモデルが該当し得る)のスコアを特許粒度に展開する経路の両方を、単一の評価入口として提供する。

- 入力: 縮約対応表、モデル予測(特許粒度 `scores_patent_{条件}.parquet` または縮約ノード粒度 `scores_node_{条件}.parquet`)、イベント表(イベント ID、クラス、正解特許番号)。
- アルゴリズム(縮約ノード粒度の入力の場合のみ手順 2 を実行):

```
1. 候補プールをイベントごとに確定する: そのイベントのクラスの
   全特許(特許粒度)。縮約条件に依存させない
2. 各イベント・各候補特許について、その特許が属する縮約ノードの
   スコアを、その特許のスコアとして継承する
3. 同点の順位は特許番号の辞書順で決定的に付ける
4. 正解特許の順位を記録する
```

- 出力: `ranks_{条件}.parquet`(列: イベント ID、正解特許番号、順位、プールサイズ)。項目 9 の指標計算はこのファイルだけを読む。
- 単体テスト(3 本): (a) 恒等写像の対応表を通した結果が、展開なしの直接評価と全順位一致する。(b) 全候補に同一スコアを与えた入力で、順位が特許番号の辞書順になる。(c) 任意の 2 つの縮約条件で、同一イベントのプールサイズが一致する。

### 項目 7: 同規模ランダム縮約の生成
**実装・学習作業 / 項目 6 と並行 / 後続: 項目 19 の統制条件**

実装 `random_contraction.py`(入力: 実縮約の対応表、特許マスタ(特許番号、クラス)):

```
1. 実縮約の対応表から、クラスごとに縮約グループのサイズの
   多重集合を取り出す
2. 同じクラスの特許を乱数で並べ替え、手順 1 と同じサイズ列で
   区切ってグループ化する(会社を無視した無作為マージ)
3. 縮約対応表と同一スキーマで書き出す
```

乱数系列 3 通り(seed = 0, 1, 2)で `contraction_map_random_{seed}.parquet` を生成。検証: クラスごとの縮約ノード数が実縮約と厳密に一致すること(単体テスト)。エッジ削減率の実縮約との差をログに出力。

### 項目 11: 候補モデルの実装
**実装・学習作業 / 調査は即日・実装はその後 / 後続: 項目 19・20**

本タスク(引用集合の補完)はハイパーグラフのハイパーエッジ補完であり、候補は **AllSetTransformer**(ICLR 2022)と **Hyper-SAGNN**(ICLR 2020)。LLM によるエッジ予測系は全候補ランキングが不可能なため「上位 50 件を Qwen3-VL で再ランクする」付録実験に限定する。

1. 実装調査: 両モデルの公開実装の保守状況・実測メモリ。結果で片方に絞る。
2. 実装・接続: 選定モデルを項目 9 の評価プログラムと現行特徴量(画像・テキスト・クラス)に接続し、現行データで動作確認。
3. 現行の DyGFormer 型モデルは継続ベースラインとして保持(項目 19 の土台)。

### 項目 14: テキストベクトルから会社名除去(製品名のみ)

### 項目 15: 三角縮約の増大(固定点)
**実装・学習作業 / 実装は 2 週目から・確定は項目 3 完了後 / 後続: 項目 19 の縮約条件**

現行の縮約(基準条件・論文どおり): 共引用グラフ上の同一会社の閉三角形を Union–Find で併合し、ノードを共有する三角形をまたいで推移的に連結する。ノードは削除せず家族代表を記録、家族内エッジは消滅、家族間エッジは多重度を重みとして保持。会社不明の特許は縮約しない。全縮約変種はこの規則(重みの保持・会社不明の除外・縮約対応表の出力)を踏襲する。

1. 理論確認: 再帰縮約(縮約後のグラフに新たに現れる同一会社三角形を、消えるまで反復して縮約)が、現行の 1 回分(元グラフ上の推移的連結)と一致するかを小規模グラフで検証。一致すれば再帰実装は不要で、反復回数対縮小量の曲線だけを出力する。
2. 固定点縮約の実装: 反復深さごとのノード・エッジ数を記録し収束曲線を出力。

### 項目 16: 双子ノード縮約
